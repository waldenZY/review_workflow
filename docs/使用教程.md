# Eval Studio 使用教程：每一步填什么、为什么填、会影响什么

适用版本：当前 v0，2026-10-27。本文按实际页面和处理逻辑编写，既说明操作，也说明当前限制。

## 先了解当前版本能验证什么

工作台评测的是**已经生成好的内容**。你提供任务输入、已有输出和可选参考资料，再告诉系统判断标准。

当前 LLM 相关环节全部使用模拟响应：候选标准提取不真正理解你的 Prompt；分析建议是模拟内容；LLM 判断也使用预设结果。只有非空、JSON Schema 等内置程序规则真正执行检查。

因此，目前能体验数据和操作流程，不能根据模拟判断判断业务内容质量。把模拟场景改成“通过”，意思是“假设裁判返回通过，检查后面的流程”，不是系统已认为你的内容合格。

## 1. 整体流程与各环节的作用

| 环节 | 你需要决定什么 | 对后续有什么影响 |
| --- | --- | --- |
| 导入数据 | 哪份已有内容要接受评测 | 决定本次可以选哪些记录和字段 |
| 字段映射 | 哪些是任务输入、待评测输出、参考依据 | 决定实际拿哪些内容组织评测请求 |
| 评测标准 | 怎样才算符合要求 | 决定每一项判断的问题、前提和方法 |
| 依据检查 | 判断这些问题所需的信息是否提供 | 提醒缺少的依据，避免把猜测当结论 |
| 评测器 | 如何组织判断指令和返回结果 | 决定请求内容、校验方式及结果读取路径 |
| 试评/执行 | 使用哪些样本、哪个已保存版本 | 创建固定数据与配置的运行记录 |
| 复核与导出 | 哪些判断需要人工修订、哪些字段要导出 | 保留人工结论、形成验证案例和结果文件 |

“评测标准”是要求，例如“摘要不得虚构原文没有的信息”；“评测器”是执行这些要求的配置，包括 Judge Prompt、模型预设和返回格式。两者分别保存，修改标准后需要更新评测器绑定的版本。

## 2. 用一条记录理解字段角色

下面只是教学用的一条数据，不是默认业务标准，也不是系统的正确答案。需要保存文件时，可在项目外的 testdata 目录保存为 UTF-8 JSON 文件；教程本身不会创建、导入或执行这条记录。

```json
[
  {
    "sample_id": "S001",
    "task_input": {
      "instruction": "根据原文写一句话摘要。",
      "source_text": "新品发布会安排在周五上午10点，地点为第一会议室。"
    },
    "generated_output": "新品发布会将于周五上午10点在第一会议室举行。",
    "reference": "活动为新品发布会；时间为周五上午10点；地点为第一会议室。"
  }
]
```

这里，task_input 是原任务交给生成模型的材料，generated_output 是已经生成的摘要，reference 是人为提供的核对资料。工作台不会自动证明参考资料正确，也不会重新生成摘要。

也可以先点击页面上的“载入一条模拟记录”体验，其字段角色与这个例子相似，具体内容无需与本例相同。

## 3. 数据管理：导入、字段路径与三列勾选框

### 3.1 如何导入

支持 JSONL、JSON、XLSX，不支持 CSV。JSON 可为单对象或对象数组；JSONL 每个非空行是一条对象记录；XLSX 需要选择工作表和表头行。

导入后先看预览：记录是否拆分正确、表头是否选对、输出是否真的存在。文件上限为 25 MB，前端每页预览 50 条。不要将“导入成功”理解为内容已完成评测。

### 3.2 “字段路径”是什么，如何读取

它是**一条记录内部某个值的位置**，不是电脑上的文件路径，也不是需要手写的代码。

对于上面的记录，页面会自动识别：

| 字段路径 | 实际读取的内容 |
| --- | --- |
| `/sample_id` | S001 |
| `/task_input` | 包含 instruction 和 source_text 的整个对象 |
| `/task_input/instruction` | 根据原文写一句话摘要。 |
| `/task_input/source_text` | 原文中的发布会安排 |
| `/generated_output` | 已生成的摘要 |
| `/reference` | 人为提供的核对资料 |

斜线表示逐层进入对象。例如 `/task_input/source_text` 就是先找到 task_input，再取它里面的 source_text。

注意以下影响：

- 选择 `/task_input` 会传入整个对象，包括全部子字段；不是只传字段名称。通常不需要再重复选择它的子字段。
- 已选父对象的子内容，即使没有单独勾选，也仍包含在这个父对象中。
- 数组保持为数组，不自动拆成多条样本。当前字段列表也不自动列出数组元素路径。
- XLSX 的列名转换成记录字段。例如列名为 answer，路径就是 `/answer`。单元格里长得像 JSON 的文本不会自动变成可展开的对象。
- 系统汇总数据集中出现过的字段。列表里存在某条路径，不代表每一条记录都有这个值，仍需检查当前样本。

特殊字段名中，斜线 `/` 写成 `~1`，波浪号 `~` 写成 `~0`。页面自动生成路径，通常按页面选择即可。

### 3.3 三列勾选框分别代表什么

它们是**给字段分配角色**，不是给数据打分，也不是三种评测标准。

| 勾选列 | 通俗含义 | 本例怎么选 | 选错的影响 |
| --- | --- | --- | --- |
| 任务输入 | 原任务要求和上下文，帮助理解应该生成什么 | `/task_input` | 少选会让判断缺上下文；把已有输出当输入会混淆评测对象 |
| 已有输出 | 真正接受评测的内容，即“要检查的作业” | `/generated_output` | 选错会检查错对象；没有输出就无法完成模式 A 的评测 |
| 参考依据 | 用来核对的原文、参考答案、检索资料、领域依据 | `/reference`，可选 | 不可靠的参考可能误导判断；没提供却强行要求核对会缺少依据 |

每种角色可以选择多个不同字段，但同一条路径只能分配一个角色。把已经勾为输入的路径改勾为输出，原来的输入勾选会取消。

sample_id、来源批次等仅用于定位时，可以不勾选。它们仍保留在原始记录和导出中。未映射的独立字段不会作为评测字段传入请求；已选择父对象所包含的子字段仍会传入。

至少选择一个已有输出字段；任务输入和参考是否需要，取决于评测标准。例如检查回答是否为空只需输出，检查摘要是否忠实于原文还需要原文。

“任务输入”和“参考依据”不总有唯一分法：原文既是生成时的输入，也能成为评测的核对材料。当前系统要求同一路径只选一个角色，可将其归入任务输入，并让相关标准声明需要“任务输入”。不必为了形式重复复制同一份材料。

### 3.4 “保存字段映射”是什么含义

它是把“哪些字段作为哪些角色”的选择保存成一份配置，并产生版本号，例如映射 v1。它不会改写原始数据，不会生成内容，不会立即执行评测。

保存后，后续步骤才能明确读取这份配置。修改勾选会成为未保存草稿，需要再次保存；新的运行使用你选定的已保存映射版本，旧运行保留原映射快照。

多个输出字段时，LLM 请求可以拿到这些输出。内置程序规则一次只检查一个“规则作用字段”；未指定时使用映射列表中的第一个输出，因此多输出场景应显式选择规则目标。

## 4. 评测标准：三个文本字段与评测方式

### 4.1 “方案名称”和“生成任务 Prompt”

方案名称是这组标准的名称，例如“一句话摘要评测”，用于查找和复用。

生成任务 Prompt 是当初要求生成模型产出内容的说明，可粘贴或读取 .md/.txt。它用于辅助设计标准，不会被执行成生成任务，也不能替代导入数据中的已有输出。不提供 Prompt 时直接手工填写标准即可。

当前“模拟提取候选标准”返回通用模拟条目，不会真正读懂 Prompt。按钮会替换当前标准草稿，应先确认需要保留的条目；提取后仍需人工修改。

### 4.2 独立标准卡片里的三个文本字段

| 字段 | 含义 | 应该填写什么 | 修改的影响 |
| --- | --- | --- | --- |
| 标准 ID | 一条标准的稳定编号 | 如 C001、C002；使用字母、数字、下划线或连字符，同一方案内不重复 | 用于结果对应、版本追踪和回归案例；仅调整措辞时应保持 ID |
| 标准名称 | 给人看的简短标题 | 如“输出非空”“摘要忠实于原文” | 影响展示；名称本身不足以定义清晰的判定条件 |
| 标准描述 | 具体判断要求和边界 | 如“摘要中的活动、时间和地点必须有原文支持；不得添加未提供的安排” | 对 LLM 判断应起实际指导作用；当前模拟 Judge 不会语义执行这些要求 |

不要只写“质量好”“内容准确”。可写明检查对象、合格条件和不确定时如何处理。

“启用”控制该标准是否参与新构建的评测器。关闭某项后保存标准，再重新构建评测器；已经保存的旧评测器仍绑定原标准版本。

### 4.3 评测方式有什么区别

| 方式 | 实际检查什么 | 是否依赖 LLM | 当前 v0 的效果 |
| --- | --- | --- | --- |
| 程序规则 · 非空 | 指定输出字段是否有内容 | 否 | 真正执行，空字符串、纯空白文本、null、空数组或空对象不能通过 |
| 程序规则 · JSON Schema | 输出能否作为 JSON 解析，且结构是否满足配置 | 否 | 真正执行，可检查字段、类型、枚举和必填项等 |
| LLM 判断（模拟） | 原计划用于语义、表达质量、任务符合性等判断 | 真实接入后需要；当前使用模拟 | 按模拟场景或自定义响应给结果，不真正判断内容 |

**标准描述不会自动变成程序代码。** 对程序规则，实际逻辑由选定规则、作用字段和 Schema 决定。即使描述写了“不能重复”，非空规则也只检查是否为空。

同样，非空规则检查的是选定值本身。一个含有空子字段的非空对象，仍可能通过；想检查内部文本，就应选择对应文本字段。

JSON Schema 方式适合输出本来就是 JSON 对象或 JSON 文本的任务。普通摘要文本不是 JSON，直接使用此规则会判格式不合格，不能用它检查摘要语义是否正确。

### 4.4 第一次可以怎样填写

对教程中的一条摘要记录，先配置两项：

| 配置 | C001 | C002 |
| --- | --- | --- |
| 名称 | 输出非空 | 摘要忠实于原文 |
| 描述 | 摘要必须有实际文本内容 | 活动、时间和地点必须有原文支持，不添加没有依据的安排 |
| 方式 | 程序规则 · 非空 | LLM 判断（模拟） |
| 必要依据 | 已有输出 | 任务输入、已有输出 |
| 规则作用字段 | `/generated_output` | 无需填写程序规则目标 |

保存后，可以真正验证 C001。C002 当前只能检查流程；想验证真实语义判断，需要以后接入模型并结合人工案例验证。

### 4.5 “必要依据”的三个选项是什么意思

它们声明的是**这条标准作判断的前提**。这里选择的是角色，不是某个具体列：

- 已有输出：需要看到被检查的内容。
- 任务输入：需要知道原任务或原文，才能判断是否符合要求。
- 参考依据：需要提供额外的对照资料，才能作出可靠判断。

这与数据管理里的角色勾选是配套关系：数据管理提供材料，标准声明需要什么材料。

当前请求仍包含所有已映射字段；“必要依据”不是逐标准过滤字段的开关。它用于基础缺失检查。非空规则只检查目标值，额外勾选参考不会给它增加语义核对能力，入门时只选已有输出即可。

## 5. “依据与可评测性”是什么

它关注的问题是：**按照这条标准，现在提供的信息够不够作判断？** 它不是在判断生成内容是否合格。

例如：

| 标准 | 已有材料 | 结论 |
| --- | --- | --- |
| 摘要是否为空 | 摘要文本 | 可以直接检查 |
| 摘要是否忠实于原文 | 只有摘要，没有原文 | 缺少核对依据 |
| 回答中的数据是否准确 | 只有回答，没有可信来源 | 不能仅凭流畅表达确认正确 |
| 输出是否采用指定格式 | 输出及格式定义 | 可以做程序结构校验 |

### 5.1 按钮现在实际做什么

“检查依据（模拟建议）”使用数据管理中选中的第一条记录；未选中时使用当前预览页的第一条。需要先保存映射和标准。

程序会对照每条标准声明的角色，检查该样本对应角色中是否至少有一个非空值；显示缺少哪些角色、可用字段，以及局限说明。额外的分析建议来自模拟响应。

它目前不会证明参考资料可信，不会核验资料是否包含回答问题所需的全部事实，也不会检查所有行。第一条有原文，不代表后面每条都有原文。

### 5.2 检查后应该怎么处理

有缺失时，按具体情况处理：回到数据管理补充或调整映射；补充真实参考资料；缩小标准范围；或暂时停用无法判断的标准。不要为了让检查通过而取消实际必需的依据要求。

检查结果和请求记录会进入设计过程，页面变为未保存状态。按需修改标准或备注，然后再次“保存标准”，再构建评测器。

依据检查不是当前强制的审批步骤，但首次配置和材料发生变化时值得检查。执行时还会按当前样本检查 LLM/结构规则的必需角色，缺少时给“依据不足”，而不是内容失败。

当前检查粒度是角色：例如映射了两份参考，只要其中一份有内容，角色就可能显示已提供。这不保证两份材料齐备或语义充分，仍需人工查看。

## 6. 评测器：把标准变成可执行配置

### 6.1 为什么标准保存后还要构建评测器

标准描述评什么，评测器把它绑定到执行指令、返回格式及解析方式。“按标准构建草稿”使用确定性模板生成配置，不是调用 LLM 自动寻找最优评测 Prompt。

页面中的 Judge Prompt 是通用判断政策。请求渲染时还会追加已确认标准与返回 Schema，并放入映射后的输入、输出及参考。因此最终请求比编辑框中的通用 Prompt 更完整，应以“实际请求预览”为准。

重新构建会将草稿重置为模板配置，包括返回结构及模拟设置。若之前做了自定义配置，应先记录需要保留的内容，再重新调整和保存。

### 6.2 模型连接字段现在有什么影响

| 字段 | 用途 | 当前 v0 影响 |
| --- | --- | --- |
| Base URL | 未来模型服务地址 | 进入请求预览，不实际访问 |
| 模型名称 | 未来使用的模型 | 进入预览和模拟响应记录，改名不改变判断质量 |
| API Key 环境变量名 | 保存密钥的环境变量名称 | 填变量名而非密钥内容；当前不会读取 |
| 预设输出模式 | 未来请求对返回格式的要求 | 改变预览请求；本地仍校验 JSON 和 Schema |
| 超时、模型参数 | 未来调用参数 | 保存到配置与预览，不产生真实模型行为 |

首次使用可保留默认配置。不要通过改模型名称来判断真实模型间效果，当前所有模型步骤仍是模拟。

### 6.3 两种 JSON Schema 不要混淆

| 位置 | 校验对象 | 失败代表什么 |
| --- | --- | --- |
| 标准选择“程序规则 · JSON Schema”时 | 原数据中的已有生成输出 | 待评测内容未满足该结构标准，可判该项 fail |
| 评测器的“评测返回 JSON Schema” | 裁判本次返回的评测 JSON | 评测器结果无法按约定读取，记为结构校验失败，不等于内容不合格 |

第一次使用保留默认的评测返回 Schema 和路径映射。它们应与同一份返回 JSON 匹配。

### 6.4 “结果路径映射”是什么

它告诉系统从裁判返回的 JSON 中，到哪里读取某条标准的判定、理由和依据。例如 C002 的返回内容可能是：

```json
{
  "criteria": {
    "C002": {
      "verdict": "insufficient_evidence",
      "reason": "这是预设模拟判断，仅用于检查流程。",
      "evidence": []
    }
  }
}
```

对应的路径映射为：

```json
[
  {
    "criterion_id": "C002",
    "verdict_path": "/criteria/C002/verdict",
    "reason_path": "/criteria/C002/reason",
    "evidence_path": "/criteria/C002/evidence"
  }
]
```

判定使用 pass、fail、insufficient_evidence、not_applicable 四种值。理由是字符串，依据是字符串数组。字段名可以自定义，但需要同步修改 Schema、路径映射和模拟正文；当前不会自动将“合格”等自定义标签翻译为 pass。

没有映射的标准可以保留原始载荷，但不会自动纳入标准统计。Schema 合法却仍找不到映射路径时，会记录路径映射失败。

本例的 C001 是程序规则，结果直接进入统一标准结果，不要求出现在模型原始返回中。不要因原始响应只有 C002，就认为 C001 被漏评。

### 6.5 模拟场景如何选择

首次保留默认“依据不足”，或者切换为“通过”查看结果展示。场景只影响实际走到 LLM 模拟步骤的标准，不会覆盖程序规则，也不会覆盖必要依据缺失检查。

非法 JSON、Schema 不匹配、调用失败用于验证故障处理。填写“自定义模拟响应正文”后，一般场景使用这份正文；故障场景优先于正文。修改返回 Schema 后，默认模拟正文可能不匹配，需要同步提供正文。

## 7. 预览与执行：先用一条确认流程

### 7.1 预览时核对什么

保存评测器后点击“预览请求”，检查：任务输入是否为正确原文，待评测输出是否为真正要检查的内容，参考是否属于这一条样本，标准与版本是否正确，以及返回结构和参数是否符合预期。

预览不创建评测结果，不触发模型调用。它的价值是发现“字段选错”或“配置没有带进请求”，不要只看请求是否能显示。

### 7.2 “试评一条”和“开始评测”

“试评一条”只使用选中的第一条；没有选中时使用当前预览页第一条。“开始评测”使用选中的记录，或用户明确勾选确认的全量范围。

当前验证只用一条。选择了多条再点击“试评一条”，并不会评完全部已选记录。

运行会固定数据、字段映射、标准和评测器版本。此后编辑配置不会偷偷改变正在执行或已经完成的运行。

### 7.3 如何理解执行状态

| 状态 | 含义 | 先检查什么 |
| --- | --- | --- |
| 已完成 | 执行和结果读取完成 | 再看各标准的内容判定；完成不等于通过 |
| 调用失败 | 模拟调用发生异常 | 是否选择了调用失败场景 |
| 解析失败 | 响应不是合法 JSON | 原始响应和自定义模拟正文 |
| 结构不匹配 | JSON 不满足返回 Schema | 缺少字段、类型或枚举是否错误 |
| 路径映射失败 | 无法按配置读取标准结果 | 映射路径和该位置的值 |
| 已跳过 | 当前行缺少已映射的输出值等 | 是否只有输入数据，或输出为 null |
| 已取消/已中断 | 任务取消或服务中断 | 是否需要用原配置重试 |

整行没有输出时会跳过；输出字段存在且是空字符串时，可由非空规则判 fail。两者不是同一种情况。

## 8. 结果、人工复核与回归案例

### 8.1 先看标准判定，再看证据与来源

| 判定 | 解释 |
| --- | --- |
| 通过 | 当前标准下给出的合格判定；模拟来源仍不是实际质量证明 |
| 不通过 | 当前标准下发现不符合要求；查看是实际规则还是模拟结果 |
| 依据不足 | 当前材料不足以支持判断，或使用了这一模拟场景 |
| 不适用 | 当前样本不在该标准的适用范围内 |

“依据不足”不等于“不通过”；“技术失败”也不等于“不通过”。结果旁的来源可区分内置规则、依据检查和 LLM 模拟。

对教程示例，C001 的非空规则应能完成真实校验；C002 在默认场景下会显示模拟的依据不足。把场景改为通过并保存新的评测器后复测，C002 可显示通过，但仍不能据此证明摘要忠实于原文。

统计数字按标准判定次数计数。一条样本包含两条标准时，可以出现两个判断，不是系统多跑了一条样本。当前不自动计算总分或总体准确率；人工修订也不会静默改写模型统计。

### 8.2 怎样人工复核

查看原始记录、标准、判断依据，必要时展开实际请求、模型原始响应、解析 JSON 和版本快照。然后选择要修订的标准、人工结论及修订理由，点击“保存复核”。

复核会追加保存，原判断和对应执行尝试仍可查看。不要为了看到“通过”而修改判定，应记录你独立核对的理由。

### 8.3 “保存为回归案例”是什么

可以理解为保存一道带有人工作答的验证题：以后修改评测器，再用同一条记录和同一标准检查判断是否与人工结论一致。

当前来源运行是模拟时，需要额外确认自己已经独立复核。系统不会自动把模拟返回当作正确答案。

案例绑定标准方案和标准 ID。标准含义变化后，旧人工结论未必适用，需重新确认；当前版本间的结果显示不代表案例已经自动重新验证。

## 9. 重试、复测与版本：修改之后该点哪个

| 操作 | 使用什么配置 | 什么时候使用 |
| --- | --- | --- |
| 原配置重试 | 原运行固定的配置，未完成记录追加执行尝试 | 排查相同配置下的异常，或继续被中断的任务 |
| 同批样本复测 | 当前已保存评测器，新建运行 | 修改标准、Prompt、Schema 或模拟设置之后比较结果 |
| 复测此案例 | 当前已保存评测器与该人工案例，新建运行 | 检查特定人工确认问题 |

如果旧运行使用“非法 JSON”场景，保存新评测器改成正常场景后，点击“原配置重试”仍会使用旧的非法 JSON 配置。这时应选择“同批样本复测”。

每次保存标准或评测器都会创建新版本。保存标准不会自动更新已经保存的评测器。

修改标准后的推荐顺序：保存标准 → 按新标准构建评测器草稿 → 恢复需要的自定义设置 → 保存评测器 → 预览 → 复测。

只修改评测器参数或模拟正文时：保存评测器 → 预览 → 复测，不需要重新提取标准。

## 10. 导出 XLSX 的含义

先选择需要导出的结果载荷路径，再点击“导出结果”。未勾选载荷字段时，仍可导出执行状态、统一标准结果和人工复核。

导出包含数据集全部原始记录，保留原列和原始行序。只评了一条时，其它行显示未运行，不会被记成内容失败。新列使用 eval. 前缀，其中 eval.payload 加结果路径表示从裁判 JSON 展开的字段。

数组和对象写为 JSON 文本；与原列名冲突或单元格超长时明确报错。原始数据内容与列受到保留，不承诺原 Excel 的样式和可执行公式无损往返。

导出后，完整运行快照还会保存到外部运行数据目录。该目录的位置可从服务健康信息查看，普通使用不需要编辑其中的文件。

## 11. 第一次使用可以照着做的最短路径

1. 点击“载入一条模拟记录”，或导入你的一条完整已有数据。
2. 将任务材料勾为任务输入，将生成结果勾为已有输出，按需勾选参考；保存字段映射。
3. 新建方案，添加一条“程序规则 · 非空”，必要依据只选已有输出。
4. 再添加一条有明确描述的 LLM 标准，声明它真正需要的角色；保存标准。
5. 检查依据，查看缺失提示与模拟建议，按需修改后再次保存标准。
6. 按标准构建评测器草稿，第一次先保留默认返回 Schema、映射和模拟配置，保存评测器。
7. 预览请求，确认字段和标准都正确，然后试评一条。
8. 查看真实非空规则与模拟 LLM 判定的来源差异，尝试人工复核并导出。

高级 JSON 编辑、模拟故障和回归案例可以在这条路径跑通后再体验。整个过程不需要执行生成任务，也不需要测试整份数据。

## 12. 遇到问题时先查这里

| 现象 | 常见原因与处理 |
| --- | --- |
| 无法保存映射 | 未选择已有输出，或映射引用了不存在的路径 |
| 已有一份输入文件，但没有可评内容 | 文件只有任务输入，没有已经生成的输出；需补充已有输出，不能将输入冒充输出 |
| 依据检查按钮不可用 | 标准或映射未保存，或没有可用于检查的记录 |
| 检查依据后又提示未保存 | 检查记录进入设计过程，需要再次保存标准 |
| 编辑了标准，运行仍像旧配置 | 评测器仍绑定旧标准版本；重新构建并保存后复测 |
| 模拟场景选通过，仍显示依据不足 | 必要角色缺失，基础依据检查先于 LLM 模拟 |
| 修改描述，结果没有语义变化 | 当前 LLM 判断是模拟；程序规则也不会把描述自动转成代码 |
| 模型返回 JSON 有效，但执行失败 | 检查是否满足 Schema，再检查结果路径和判定枚举 |
| 一条记录显示两个通过 | 数字统计的是两条标准的判断，不是两条记录 |
| 人工改判后原结果还在 | 这是留痕设计，人工结论追加保存，不覆盖原判断 |
| 换了评测器，原配置重试仍失败 | 原运行配置固定；使用当前评测器新建复测 |

本教程解释的是当前功能，不表示模拟步骤已经具备真实语义评测能力。启动和部署问题另见 [Linux 部署](Linux部署.md)，工程边界见 [v0 实现与验收](v0实现与验收.md)。
