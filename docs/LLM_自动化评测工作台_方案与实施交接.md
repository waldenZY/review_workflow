# LLM 自动化评测工作台：方案与实施交接文档

> **文档性质**：需求与演进方案（供产品/研发/算法共同评审，不等同于已冻结的详细技术设计）  
> **整理日期**：2026-10-27  
> **当前阶段**：仅聚焦**模式 A：对已有 LLM 输出进行评测**；建设 P1 基础工作台与 P2 智能评测设计的第一版。  
> **状态说明**：本文以「已确定 / 实现建议 / 待确认」区分讨论共识与新增设计建议；实现前需对待确认项做一次轻量决策。

## 1. 项目背景与目标

日常工作涉及对不同 LLM 任务的生成内容进行质量评测。目前重复劳动主要包括：处理多格式数据与字段、编写和修改评测 Prompt、逐条或脚本批量调用模型、整理结构化结果、人工检查误判、总结失败模式。更困难的是：**评测标准本身是否足够清晰、可判断，以及 LLM 裁判执行这些标准是否可靠**。

### 1.1 目标（已确定）

- **短期**：提供有 Web 界面的通用自动化评测工具，覆盖实际工作的多种 LLM 已生成内容，减少人工处理成本、降低明显误判，提升评测效率。
- **中期**：从生成任务 Prompt 中辅助提取可编辑的评测标准，识别所需评测依据，自动形成可执行的评测方案，并通过试评测与人工纠错持续优化。
- **长期**：演进为能够辅助**构建、验证、迭代、复用可靠评测标准和评测器**的系统；不以“自动生成一段更长的评测 Prompt”为终点。

### 1.2 核心原则（已确定/讨论共识）

1. **确定性工作流为主，LLM 在需要理解、判断、分析的节点提供能力**；第一阶段不为追求 Agent 形态引入复杂自主编排。
2. **任务生成要求 ≠ 可直接执行的评测标准**。自动提取的标准是候选方案，必须允许人工审阅与修正。
3. **评测标准和评测器实现分离**：标准描述“评什么”，评测器描述“如何评”；两者均应可版本化。
4. **评测结果与结果分析分离**：逐条的主观内容判断发生在评测阶段；批跑后的失败归类、原因推测、改进建议属于后分析阶段。
5. **可追踪、可复现、可复核优先**：保存输入映射、标准与评测器版本、原始响应、解析后的结果及执行状态。
6. **不能把证据不足包装成确定结论**：支持“不足以判断 / 不适用”等结果，并明确人工审核及外部依据的作用。

## 2. 本阶段的范围与非目标

### 2.1 纳入范围（已确定）

- 导入已有样本及其 LLM 输出：`JSONL`、`JSON`、`XLSX`、`CSV`。
- 自动识别字段；用户指定参与评测的输入字段、待评测输出字段、可选参考依据字段。
- 两种标准来源：① 提供**生成任务 Prompt**（文本或 Markdown），系统辅助提取；② 不提供 Prompt，由用户手动录入评测要求/标准。
- 用户能够查看、编辑、增删、启停提取的标准，确认后生成可执行的评测器（包含评测 Prompt，必要时包含程序规则）。
- 用户能够自定义评测返回的 JSON 结构/字段，解析后追加到原数据，最终导出 XLSX。
- 支持选中部分样本或全量批跑，提供试评测、进度、失败及重试等基础能力。
- 逐条评测可以调用 LLM；批跑后可以调用 LLM 做失败样本归类、原因分析和改进建议。
- 保存评测配置与执行记录；支持人工检查、纠正部分评测结果，并逐步沉淀验证样本。

### 2.2 暂不纳入（已确定）

- **模式 B：自动调用生成模型生产待评测内容**。
- 多生成 Prompt/多生成模型的端到端效果对比平台。
- 拖拽式通用 Agent 工作流编排、多智能体协作。
- 多租户/复杂团队权限、完整人工标注平台。
- 自动优化并直接改写生产环境中的生成 Prompt。

> 注：这些能力并非永远不做；第一版只在数据模型上避免阻断将来扩展。

## 3. 用户工作流（目标流程）

```text
导入已有数据文件
    ↓
预览数据 → 识别字段 → 映射评测输入/待评测输出/参考依据
    ↓
创建评测方案
    ├─ 输入生成任务 Prompt → LLM 提取候选标准
    └─ 未提供生成 Prompt → 手动输入标准
    ↓
识别评测方法、必要依据和能力边界 → 人工编辑、确认
    ↓
配置评测器（规则/LLM、模型参数、提示词、返回 JSON Schema）
    ↓
预览实际拼接请求 → 选取小样本试评测 → 人工检查与修改
    ↓
选择全量/部分/筛选/抽样数据 → 批量运行
    ↓
逐条评测结果 + 执行日志 → 汇总统计 → LLM 失败分析（可选）
    ↓
导出保留原列的 XLSX；保存数据集、标准、评测器与运行版本
```

Web 界面建议使用五个主功能区：**数据管理 → 评测标准 → 评测配置 → 执行任务 → 结果分析**。这是信息架构建议，不要求第一版做复杂可视化画布。

## 4. 功能需求

### 4.1 P1：评测基础工作台（第一优先级）

| 编号 | 功能 | 第一版要求 | 优先级 |
|---|---|---|---|
| P1-01 | 多格式导入 | 支持 JSONL、JSON、CSV、XLSX；显示记录数、字段、样本预览；非法文件给出可理解的错误 | 必须 |
| P1-02 | 字段映射 | 用户可选多个上下文/任务输入字段，指定至少一个待评测输出字段；参考答案/知识依据为可选；保存映射 | 必须 |
| P1-03 | 手动标准 | 即使没有生成任务 Prompt，也能手动定义、编辑评测标准并完成评测 | 必须 |
| P1-04 | 评测器配置 | 设置模型连接、评测 Prompt、评测使用字段、输出 JSON 结构；能看到一条样本渲染后的实际请求 | 必须 |
| P1-05 | 结构化结果 | 验证 JSON 解析结果与目标结构；记录解析失败、原始响应与错误信息；支持用户选择导出字段 | 必须 |
| P1-06 | 选择与执行 | 全量、指定行/部分样本运行；可查看进度、成功/失败/跳过状态，支持基本失败重试 | 必须 |
| P1-07 | 导出 | 原始数据列保持不变，将解析后的评测字段追加为新列，导出 XLSX；保留样本定位标识 | 必须 |
| P1-08 | 配置持久化 | 保存数据集引用、字段映射、标准版本、评测器配置及执行记录，支持之后重新运行 | 必须 |
| P1-09 | 筛选与抽样 | 按条件筛选、随机抽样、指定区间运行 | 建议首版或紧随其后 |
| P1-10 | 稳定运行 | 并发限制、超时、取消任务、继续/重试、使用量统计 | 可随使用规模逐步完善 |

**数据格式细节（实现建议）**：将数据导入后规范化为“有稳定 `row_id` 的记录集合”。JSON/JSONL 优先支持“对象数组/逐行对象”，对嵌套字段提供路径选择；XLSX 提供 Sheet 选择；原始文件或原始行数据与规范化记录关联。复杂 JSON、数组展开、空值以及列名冲突的处理规则需明确并提示用户，不应静默丢字段。

### 4.2 P2-A：生成 Prompt → 候选评测标准（当前阶段基础版）

- 接受粘贴文本或上传 `.md`/`.txt` 形式的**生成任务 Prompt**；它是评测要求的来源，不代表本阶段要执行生成任务。
- LLM 辅助识别：任务目标、强制约束、格式要求、质量维度、潜在冲突或歧义。
- 输出为**结构化候选标准**，而非仅输出一段不可拆分的评测 Prompt。
- 用户可新增、删除、修改、启停和合并标准；修改后再进入评测器构建。
- 无生成 Prompt 时，走手动创建标准的路径；不强制自动提取。

### 4.3 P2-B：标准可评测性与依据分析（当前阶段基础版）

系统对每条候选标准建议：

- **推荐评测方式**：程序规则 / LLM 主观判断 / 混合判断 / 暂不能可靠判断。
- **需要的证据**：仅待评测输出即可；还需要任务输入；还需要参考答案/知识库/领域标准；或依赖尚不存在的信息。
- **不足和风险**：表达模糊、范围不清、标准间可能冲突、事实依据不足、容易产生猜测性判断等。
- **可执行策略**：可直接执行；允许探索性执行但需标记不确定性；暂缓执行；要求补充依据。最终由用户确认。

不要仅凭生成 Prompt 宣称某条标准“必然能被准确验证”。这一步的结果主要用于辅助配置和显露风险。

### 4.4 P2-C：评测器生成、执行与校准（长期优化重点）

- 将已确认的标准转化为具体评测实现：程序校验逻辑或 LLM Judge Prompt（必要时可组合）。
- 显示评测器实际使用的输入字段、标准、裁判模型、输出结构与完整请求预览。
- 先选小样本试评测；用户可以复核结果、标记误判、修改标准或评测器后再运行。
- 可将人工确认的样本保存为**验证/回归案例**，用于不同评测器版本的同例比较。
- **第一版不要求自动搜索全局最优评测 Prompt**；优先支持清晰的误判定位及可重跑的实验。

评测结果建议至少区分：`pass`、`fail`、`insufficient_evidence`（证据不足）、`not_applicable`（不适用）。**执行状态**（成功、调用失败、解析失败、跳过）要另设字段，不能与评测结论混在一起。若未来有打分制，可额外加入分数与评分依据；无需所有任务统一成二分类。

### 4.5 P2-D：批跑后分析（当前阶段可提供基础版）

- 程序先做可信的描述性统计：各标准通过/失败/证据不足/不适用数量、失败率、解析错误数量、涉及样本等。
- 根据逐条评测结果及必要的原始样本，调用 LLM：对失败样本分组、归纳常见问题、提出潜在成因及改进建议。
- 输出应区分**可直接观察的现象和证据**、**模型推测的原因**、**建议进一步验证的改进方向**。
- 后分析不得在无明确复评机制的情况下悄悄覆盖前面逐条评测结论。
- 第一版可通过一次或少量 LLM 调用实现；不依赖 Agent 框架。若样本较多，应分批聚合，避免超出上下文限制。

**术语区分**：这里“主观内容判断”属于 P2-C 的逐条 Judge；“整体总结”属于 P2-D 的批量结果分析，二者不应合并为同一步。

## 5. 核心数据对象与关系（实现建议）

建议至少有四类可追踪的对象：

| 对象 | 主要含义 | 推荐保留的信息 |
|---|---|---|
| `Dataset` | 评测输入的数据集 | 文件来源、格式、字段元数据、行 ID、原始内容/引用、导入与映射信息 |
| `EvaluationSpec` | **评什么** | 标准条目、依据要求、适用范围、人工修改、版本、创建来源（生成 Prompt/手动） |
| `Evaluator` | **怎么评** | 标准版本引用、程序规则、Judge Prompt、裁判模型/参数、响应 JSON Schema、版本 |
| `EvaluationRun` | **哪次运行** | 数据集/行选择、评测器版本、开始结束状态、逐行原始响应、解析结果、错误、统计与导出引用 |

另可附属 `ValidationCase`（人工确认的回归案例）、`AnalysisReport`（某次运行的批量诊断报告），初期不一定需要独立数据库表，但要避免覆盖旧版本。

### 5.1 单条评测标准示意（非最终协议）

```json
{
  "id": "C001",
  "name": "正文排版可读性",
  "description": "多个独立知识点应合理分段或分点，不因简洁性而堆积成整段",
  "method": "llm_judge",
  "required_roles": ["model_output"],
  "evidence_requirement": "output_only",
  "result_type": "verdict",
  "enabled": true
}
```

实现时允许追加评分、权重、适用条件、风险提示和用户备注，但不建议首版让权重与总分模型主导整个系统。

### 5.2 自定义 JSON 返回结构与 Excel 追加列

用户可以定义目标 JSON Schema，系统应校验返回结构并展示字段展开预览，例如：

```json
{
  "overall": {
    "verdict": "fail",
    "reason": "正文存在多处独立知识点堆叠"
  },
  "criteria": {
    "C001": { "verdict": "fail", "evidence": "..." }
  }
}
```

可能展开为 `overall.verdict`、`overall.reason`、`criteria.C001.verdict`、`criteria.C001.evidence` 等列。建议**内部保留统一结果信封**（行 ID、调用状态、原始响应、解析结果、标准/评测器版本），用户定义的 JSON Schema 负责具体评测载荷；导出时按用户选择投影到新列。避免自定义 JSON 破坏日志、复现与后续统计所需的内部字段。

导出行为：保留原列、保持行顺序（可配置按原顺序）、追加新列；未参与评测的行有明确空值/未运行状态；原始列名与导出字段冲突时不得无提示覆盖。

## 6. 降低误判：必要的验证闭环

**仅有自动提取和批跑不能保证误判降低**；必须让误判可识别、可纠正、可用于回归。

1. 试评测：用户选取代表性样本（可先试 10～30 条，数量只是经验建议，不是硬门槛）。
2. 人工复核：能查看原数据、评测输入、最终请求、模型原始返回、每项标准的结论和依据。
3. 记录误判：区分“评测标准不合理”“证据缺失”“评测器执行错误”“解析/调用异常”等问题。
4. 修改后复测：固定同一批回归样本，对比修改前后错误的变化；避免修复旧问题同时引入新问题。
5. 按条件呈现可靠性：有人工标签时可计算误报、漏报、分类一致程度；标签太少时只报告小样本观察，不宣称总体准确率。

一个需要长期积累的资产是**“标准 + 已人工确认的正例/反例/边界例”**，而不仅是评测 Prompt 文本。

## 7. 分阶段实施与交付

| 阶段 | 交付重点 | 完成后应具备的能力 |
|---|---|---|
| M1：P1 闭环 | 文件导入、字段映射、手动标准、配置 Judge、定制 JSON、部分/全量执行、XLSX 导出 | 无生成 Prompt 时也能完成一次可追踪的批评测 |
| M2：P2-A/B 基础 | 生成 Prompt 自动抽取标准、用户编辑、识别所需依据和可评测性风险 | 从任务说明快速得到可编辑、可执行的候选评测方案 |
| M3：P2-C/D 基础 | 小样本试评测、人工纠错与回归案例、基础失败统计、LLM 失败归类及建议 | 能发现并追踪典型误判，能解释一批失败结果 |
| 长期迭代 | 标准提取质量、Judge 可靠性、不同任务适配、评测策略选择、验证案例复用、成本优化 | 逐渐降低建立可靠评测方案的成本，而不只是提高调用速度 |

M1/M2/M3 是**推荐的开发顺序，不代表业务上只验收 M1**；当前总体目标是完成 P1 + P2 的实用基础版。避免第一版投入多模型复杂评测框架或拖拽编排。

## 8. 第一阶段验收场景（建议作为测试用例）

1. **格式通路**：四种格式均能正确导入、预览、识别字段；不支持的数据形态明确告知，不会静默错配数据。
2. **模式 A 端到端**：上传包含任务输入、已有模型输出的数据，手工配置标准，选择部分样本执行，结果写回新增列并导出 XLSX；原数据没有被意外改写。
3. **生成 Prompt 提取**：上传一份 Markdown 生成 Prompt，能形成多条独立、可编辑标准；用户可禁用不合适的条目后继续评测。
4. **缺少依据**：某项质量要求依赖参考知识但数据集中没有相应字段，系统能提示限制，不会默认把模型猜测当作已验证事实。
5. **自定义返回结构**：用户修改 JSON Schema 后，成功样本按配置解析、展平并追加列；不合法 JSON/缺字段保留错误与原始响应。
6. **逐条评测与汇总分离**：能查看每条标准的判定和证据；批跑后分析可产生问题分类、样本引用、潜在成因和建议，且不覆盖逐条判定。
7. **误判回归**：人工纠正一条错误判断并保存为验证案例，修改评测器后可在相同数据上重新运行、对比结果。
8. **可复现性**：同一条评测结果可以追溯到对应的数据、字段映射、标准版本、评测器版本与模型配置。

## 9. 风险、工程边界与质量要求

- **判断依据不足**：不是所有质量要求都能从输出文本本身判断；必要时要求映射参考数据，或者输出“证据不足”。
- **Judge 偏差和波动**：结构化 JSON 并不代表判断正确；须通过人工案例、分标准回归、必要的重复运行来验证。
- **生成 Prompt 歧义**：生成要求可能冲突或遗漏；提取系统只能提供候选标准，人工确认仍然必要。
- **错误归因过度自信**：LLM 分析的“原因”常属于假设，需要支持它的样本证据和后续验证。
- **数据安全**：业务数据和模型输出可能敏感；评估模型供应商、保留期限、密钥存储、日志脱敏与访问权限。评测数据本身属于不可信内容，不应被当作新的系统指令执行。
- **大批量稳定性**：评测任务应可监控进度、保留失败记录、防止重复回写；按需支持并发限制、限流与重试。
- **结果解释性**：不要把 API 调用失败/JSON 解析失败统计成模型生成内容的不合格；统计口径应可查询。
- **成本与效率**：记录至少样本数、模型使用情况、失败/重试次数，若供应商提供 token/费用数据可进一步统计。

## 11. 供研发团队执行的建议

1. **先冻结模式 A 的输入/输出协议与版本化对象**，再设计页面。优先验证“用户选择哪些字段、传给 Judge 什么、返回什么、如何写回原数据”。
2. **不要让所有功能依赖自动标准提取成功**：标准提取失败时，仍应允许手动标准完成评测。
3. **不要将所有标准强制转换为单一 LLM Pass/Fail**：保留程序规则、可用证据和证据不足的表示。
4. **把“试评测—人工修改—回归测试”设计成正式操作路径**，而不是要求用户自行反复导出后离线分析。
5. **保存原始 LLM 请求/响应和解析状态**，同时提供适当的数据安全开关；便于分辨是标准、Judge 还是工程管线导致错误。
6. **后续 P2 的优化应有明确评价口径**：标准提取的覆盖/冗余与误提取；Judge 的误报/漏报与一致性；单批运行成本、耗时、解析失败率等。

---

### 一句话总结

**第一版是“对已有 LLM 输出进行评测”的 Web 工作台：P1 提供稳定的数据与批跑链路，P2 提供可编辑的智能标准提取、评测器构建和基础问题分析；长期重点不是 Agent 化，而是借助人工验证案例与版本化回归，不断提高评测标准和评测判断的可靠性。**
