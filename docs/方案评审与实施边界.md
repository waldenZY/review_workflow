# 方案评审与实施边界

评审日期：2026-10-27。依据：[原始方案与实施交接](LLM_自动化评测工作台_方案与实施交接.md)。本文记录新链路实施建议，不改写原需求文档，也不表示功能已经实现。

后续状态：同日已按确认的 v0 范围实现基础闭环，当前行为见 [v0 实现与验收](v0实现与验收.md)。导入范围调整为 JSONL、JSON、XLSX，不包含 CSV；以下保留设计评审背景。

## 1. 保留的方向

模式 A、Web 界面、多格式导入、手动与自动辅助两种标准来源、标准与评测器分离、执行与后分析分离、依据不足时显式表达限制，适合作为第一阶段边界。

原方案已覆盖这些原则；当前主要问题是分期、协议细节和验收口径尚未完全对齐，而不是缺少功能列表。

## 2. 应优先调整的实施顺序

| 项目 | 原方案中的张力 | 重建建议 |
| --- | --- | --- |
| 试评与人工复核 | 核心工作流强调先试评，但阶段表将试评和人工纠错列入 M3 | M1 即提供指定一条、实际请求预览、原始返回查看及人工修订留痕；批量误判归类和版本比较页面后置 |
| 批量运行 | M1 包含全量，但当前需求是节省调用、先跑通 | 当前只验证一条；以后单独增加明确的批量选择与预览，不默认执行全量 |
| 规则评测 | 方案允许程序规则，但没有定义规则来源与执行边界 | 先提供明确参数的内置校验器；自动提取只建议规则，不直接执行 LLM 生成的 Python 或任意代码 |
| 自定义 JSON | 允许任意载荷，但统计又依赖逐标准结论 | 定义结果投影：哪些路径关联标准 ID、判定、依据、分数；未建立映射的载荷可保存和导出，但不能臆造统一通过率 |
| 可靠性验证 | 一条跑通与减少误判是不同验收目标 | 当前验收工程通路；可靠性后续依靠人工确认案例检验，不能用一次模拟或一次 Judge 判断证明 |

第一条纵向闭环：导入已有记录 → 映射输入/输出/依据 → 手动配置独立标准 → 构建评测器 → 预览一条请求 → 执行一条 → 查看解析与判定 → 人工复核 → 追加列导出并保存快照。

该闭环之后补齐其余格式适配与导入边界，再实现自动提取和依据分析。失败聚类与改进建议属于后续分析能力，不阻塞基础闭环。

## 3. 最小对象与边界

以下为后续协议设计的起点，字段名称尚未冻结。

| 对象 | 必须明确的内容 |
| --- | --- |
| Dataset | 不改写的原始记录、内部稳定 row_id、外部业务 ID、来源行/工作表；样本 ID 缺失或重复也能定位 |
| FieldMapping | 多个输入字段、至少一个已有输出字段、可选参考字段；映射有独立版本或随运行快照固定 |
| EvaluationSpec | 独立且稳定的标准 ID、描述、适用条件、依据要求、判定/评分定义、启停、来源及版本 |
| Evaluator | 引用标准版本、内置规则/LLM 实现、Judge Prompt、模型与参数、响应 Schema、结果投影、版本 |
| EvaluationRun | 数据与映射快照、明确选中行、标准及评测器版本、每次调用记录、解析结果、状态与导出配置 |
| HumanReview / ValidationCase | 原始判断、人工修订、原因、所依据的标准版本；更新标准后允许重新确认旧标签 |

版本引用必须能恢复到具体内容。仅记录会变动的文件路径或哈希，不足以恢复配置。运行开始时固定数据与配置，保存可恢复的快照或不可变内容引用；调用记录可保留敏感字段的受控引用，密钥不进入快照。

“可复现”指能还原输入、配置与请求并追溯结果，不承诺远端 LLM 重跑得到逐字相同的输出。

## 4. 判定、执行与统计

- 执行状态独立记录，例如未运行、运行中、完成、调用失败、解析失败、Schema 校验失败、跳过、取消；重试以 attempt 留痕。
- 标准判定可包括 pass、fail、insufficient_evidence、not_applicable，评分制保留自己的定义。业务输出本身的标签不直接当作评测判定。
- 缺少整条输出时，不能静默调用生成模型补齐，也不能默认认定所有标准均失败；应提示修正映射或补充数据。已确认应交付但实际为空的输出，则可按用户定义的完整性标准判定。
- 一项依据不足不必阻塞其它独立且可判断的标准。字段存在不等于内容充分，仍需按当前行检查。
- 未定义总分或聚合政策时，不自动生成 overall 结论，不对多项标准做隐含平均。
- 报告通过率时，说明分母以及证据不足、不适用、技术错误如何处理；技术错误不能记成内容不合格。
- 后分析报告引用 run_id、row_id、标准 ID 和可观察证据；推测原因单独标记，不覆盖原始判断。

自定义载荷要同时通过 JSON 解析、Schema 校验以及必要的语义约束检查，例如标准 ID 是否完整且无重复。Schema 合法不等于判断正确。

## 5. 导入与导出需要提前定下的规则

- 自动识别只提供字段映射建议，角色必须可见、可改；不能凭字段名替用户作最终决定。
- JSON/JSONL 首先支持对象记录，嵌套路径与数组作为显式结构保留；不默认展开数组、增加样本数或改变评测单位。
- XLSX 要选择工作表和表头；CSV 的编码、分隔符，空表头/重复表头，以及空值与空字符串要有清晰处理规则。
- XLSX 公式、日期、前导零 ID、嵌套对象等需要可见的读取策略，不能无声改变含义。第一版不承诺原工作簿全部样式与公式的无损往返。
- 保留原记录与行序，评测列使用独立命名空间并处理冲突；未选中行明确记为未运行。
- 导出的内容按文本处理，避免文本被误当作公式；超过单元格长度或表格容量时报告限制并保留完整外部产物，不静默截断。

## 6. 当前阶段边界

原评审阶段完成方案阅读、样例结构观察与旧链路删除。后续在同一 Git 仓库实现新的 Web 应用，模型步骤仅使用模拟响应；旧脚本、任务配置、产物及归档备份不再保留在工作区。

当前使用独立合成记录验证工程通路；所观察的外部测试样例缺少已生成输出，不自动补跑生成任务，背景见[单条任务流说明](样例输入与单条任务流.md)。真实模型接入和判断质量后续验证。
